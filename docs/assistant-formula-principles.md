## 🎯 1. เป้าหมายและหลักการแม่

ฟีเจอร์นี้ไม่ได้แข่งกับเครื่องคิดเลข แต่แข่งกับ **"ช่างต้องเดา"** เป้าหมายคือช่างยืนอยู่หน้างาน กรอกเลข 3–4 ช่อง แล้วได้คำตอบที่กล้าเอาไปสั่งของหรือคุยกับลูกค้าได้ทันที

หลักการแม่ 5 ข้อ เรียงตามลำดับความสำคัญ ถ้าขัดกันให้ยึดข้อที่มาก่อน

| ลำดับ | หลักการ | ความหมายเวลาลงมือ |
|---|---|---|
| 1️⃣ | **ถูกต้องก่อนสวย** | ตัวเลขผิดคือคนเสียเงินจริง เสียของจริง ห้ามเดาค่าคงที่แล้วค่อยหาที่มาทีหลัง |
| 2️⃣ | **อ้างอิงได้ทุกตัวเลข** | ทุกค่าคงที่ต้องชี้แหล่งได้ว่ามาจากมาตรฐานอะไร ข้อไหน ปีอะไร |
| 3️⃣ | **โปร่งใส กางสูตรให้ดู** | ช่างมีสิทธิ์รู้ว่าเลขนี้มาจากไหน ไม่ใช่กล่องดำ — และการกางสูตรทำให้จับ input ที่กรอกผิดได้เอง |
| 4️⃣ | **เข้าใจง่ายแบบพี่ช่างสอนน้อง** | ภาษาหน้างาน ไม่ใช่ภาษาตำรา แต่ห้ามง่ายจนบิดความหมายทางเทคนิค |
| 5️⃣ | **รู้ขอบเขตตัวเอง** | งานที่ต้องมีวิศวกรเซ็น ต้องบอกตรง ๆ ว่านี่เป็นค่าประมาณเพื่อเตรียมงาน ไม่ใช่แบบคำนวณ |

## 📚 2. ลำดับชั้นความน่าเชื่อถือของแหล่งอ้างอิง

เวลาหาค่าคงที่ ให้ไล่จากชั้นบนลงล่าง **เจอชั้นบนแล้วห้ามใช้ชั้นล่างมาขัด**

| ชั้น | แหล่ง | ตัวอย่าง | ใช้ได้แค่ไหน |
|---|---|---|---|
| 🥇 **T1** | กฎหมาย / กฎกระทรวง | กฎกระทรวงควบคุมอาคาร (ขนาดลูกตั้งลูกนอนบันได, ความสูงราวกันตก) | ผูกมัด ต้องทำตาม ห้ามมีสูตรที่แนะนำค่าที่ผิดกฎหมาย |
| 🥈 **T2** | มาตรฐานวิชาชีพ / มาตรฐานชาติ | มอก., วสท. (EIT), มยผ. (กรมโยธาธิการฯ) | เป็นค่าอ้างอิงหลักสำหรับตลาดไทย |
| 🥉 **T3** | มาตรฐานสากล | ISO, IEC, EN, ASTM, ASHRAE | ใช้เมื่อไม่มีมาตรฐานไทย หรือใช้ยืนยันมาตรฐานไทย |
| 4️⃣ **T4** | เอกสารเทคนิคผู้ผลิต (TDS / คู่มือติดตั้ง) | อัตราการใช้ปูนกาวต่อเบอร์เกรียง, ระยะเจาะบานพับ Blum/Hettich, ตาราง P–T น้ำยาแอร์ | ใช้ได้ แต่ต้องระบุว่าเป็นค่าของยี่ห้อ/ระบบนั้น และให้ผู้ใช้ปรับได้ |
| 5️⃣ **T5** | แนวปฏิบัติช่างที่ใช้กันแพร่หลาย | ตัวคูณ BTU ต่อ ตร.ม., เปอร์เซ็นต์เผื่อเสียกระเบื้อง | ใช้ได้เมื่อไม่มีมาตรฐานรองรับ ต้องเขียนกำกับว่าเป็น "แนวปฏิบัติ" ไม่ใช่มาตรฐาน และต้องมีแหล่งอ้างอิงอย่างน้อย 2 แหล่งที่สอดคล้องกัน |

### 🚫 ห้ามใช้เป็นแหล่งอ้างอิงเดี่ยว

- ❌ บล็อกขายของ / หน้าสินค้า ที่ไม่มีตัวเลขต้นทางจากมาตรฐานหรือ TDS
- ❌ เครื่องคิดเลขออนไลน์เจ้าอื่น (เอามาเทียบผลได้ แต่ห้ามอ้างเป็นที่มา)
- ❌ คำตอบจาก LLM ล้วน ๆ โดยไม่มีเอกสารรองรับ
- ❌ ค่าที่ "จำมาจากหน้างาน" โดยไม่มีใครยืนยัน

## 🔢 4. กฎการเขียนสูตร (บังคับ)

### 4.1 ค่าคงที่ทุกตัวต้องมีทะเบียน

ห้ามมี magic number ลอยในไฟล์สูตร ทุกค่าไปอยู่ใน `src/lib/chang/constants.ts` โดยมีฟิลด์ที่มาบังคับ

```ts
// ✅ ถูก
kg = area * MASONRY.plasterPerM2PerMm.value * thicknessMm;

// ❌ ผิด — เลขลอย ไม่มีใครรู้ว่ามาจากไหน
kg = area * 1.6 * thicknessMm;
```

ทุกรายการต้องมีครบ 5 อย่าง: **ค่า · หน่วย · ชื่อที่คนอ่านเข้าใจ · แหล่งอ้างอิง · ช่วงที่ยอมรับได้**

### 4.2 คิดด้วยหน่วย SI ข้างใน แปลงตอนแสดงผล

ข้างในสูตรใช้ เมตร / กิโลกรัม / วินาที / วัตต์ เสมอ ส่วนหน่วยหน้างาน (นิ้ว, ศอก, BTU, แกลลอน, ถุง, ก้อน) เป็นเรื่องของชั้นแสดงผล วิธีนี้กันบั๊กหน่วยปนกันซึ่งเป็นบั๊กที่หายากที่สุดในระบบคำนวณ

### 4.3 ตัวคูณหน่วยตามนิยาม ห้ามปัด

| หน่วย | ค่าที่ต้องใช้ | หมายเหตุ |
|---|---|---|
| 1 นิ้ว | 25.4 มม. | นิยามสากล ห้ามใช้ 25 |
| 1 ฟุต | 0.3048 ม. | |
| 1 ศอก | 0.50 ม. | หน่วยไทย |
| 1 วา | 2.00 ม. | |
| 1 ตารางวา | 4.00 ตร.ม. | |
| 1 งาน | 400 ตร.ม. | |
| 1 ไร่ | 1,600 ตร.ม. | |
| 1 แกลลอน (สีไทย) | 3.785 ลิตร | ถังใหญ่ = 18.925 ลิตร |
| g (แรงโน้มถ่วง) | 9.80665 ม./วินาที² | ห้ามใช้ 9.8 หรือ 10 |

### 4.4 ปัดเลขที่ปลายทางเท่านั้น

คำนวณด้วยความละเอียดเต็มตลอดสาย แล้วปัดตอนแสดงผลครั้งเดียว การปัดกลางทางแล้วเอาไปคูณต่อ ทำให้ผลเพี้ยนสะสม

### 4.5 ของที่ซื้อเป็นชิ้น/ถุง ต้องปัดขึ้น

ถุงปูน แผ่นกระเบื้อง ม้วนวอลเปเปอร์ หลอดซิลิโคน สกรู → `ceil()` เสมอ พร้อมบอกเศษที่เหลือด้วยถ้าเป็นประโยชน์ ("เหลือ 0.3 ถุง")

### 4.6 เผื่อเสียเป็นตัวเลือกของผู้ใช้ ไม่ใช่ค่าที่ซ่อนไว้

เปอร์เซ็นต์เผื่อเสียต้องเป็นฟิลด์ที่เห็นและแก้ได้ พร้อมค่าตั้งต้นที่อธิบายเหตุผล (ปูตรง 5% / ทแยง 10% / ก้างปลา 15%) ห้ามบวกเผื่อเงียบ ๆ ในสูตร เพราะช่างบางคนคิดเผื่อเองอยู่แล้ว จะกลายเป็นเผื่อสองรอบ

### 4.7 ห้าม clamp เงียบ

ถ้าอินพุตหลุดช่วงที่สูตรใช้ได้ (เช่น ท่อยาวเกินตารางอ้างอิง, เพดานสูง 6 เมตร, ช่วงคาน 12 เมตร) ต้อง **บอกผู้ใช้** ว่าเกินช่วงและผลลัพธ์เริ่มไม่น่าเชื่อถือ ห้ามหนีบค่าให้อยู่ในตารางแล้วตอบเฉยเหมือนปกติ

### 4.8 ค่าที่มาตรฐานให้เป็นช่วง ให้ใช้กลางช่วงและบอกช่วง

เช่นตัวคูณห้องนอน 700–750 → ใช้ 725 แล้วเขียนกำกับว่า "ช่วงมาตรฐาน 700–750" ผู้ใช้จะรู้ว่ามีที่ให้ขยับ

### 4.9 หน่วยติดกับตัวเลขทุกจุดที่แสดงผล

ทั้งในผลลัพธ์ ในบล็อกสูตร ในข้อความคัดลอก และในรูป PNG — ตัวเลขเปล่าคือต้นเหตุของการสั่งของผิด

## 🚦 5. จัดชั้นความเสี่ยง แล้วปฏิบัติตามชั้น

ทุกเครื่องมือต้องถูกจัดชั้นก่อนปล่อย

| ชั้น | ถ้าคำนวณผิดจะเกิดอะไร | ตัวอย่าง | สิ่งที่ต้องมี |
|---|---|---|---|
| 🟢 **A — เสียเงิน** | ซื้อของขาดหรือเกิน | จำนวนกระเบื้อง, ปูนฉาบกี่ถุง, สีกี่แกลลอน, แปลงหน่วย | คำอธิบายสูตร + ที่มา |
| 🟡 **B — ระบบเสียหาย / งานต้องรื้อ** | ของพังภายหลัง เสียค่าแก้ | ขนาดแอร์, ขนาดปั๊ม, ความลาดท่อ, จำนวนบานพับ, ระยะเผื่อขยายตัว | A + ระบุสมมติฐานที่ใช้ + เตือนกรณีที่สูตรใช้ไม่ได้ |
| 🔴 **C — กระทบความปลอดภัย/โครงสร้าง** | ไฟไหม้ ของหล่น คนเจ็บ | ขนาดสายไฟ-เบรกเกอร์, ความหนากระจกรับแรงลม, ระยะโก่งคาน, พุกรับน้ำหนัก, บันได | B + **ข้อความสงวนสิทธิ์แบบบังคับแสดง** ว่าเป็นค่าประมาณเพื่อเตรียมงาน ต้องให้ผู้มีใบอนุญาต/วิศวกรตรวจสอบก่อนใช้จริง + อ้างอิงมาตรฐานชัดเจน |

ข้อความสงวนสิทธิ์ของชั้น C ต้องอยู่ในฟิลด์ `caveats` ของตัวสูตร **ไม่ใช่ซ่อนในข้อความ tip** เพราะ tip ถูกเขียนทับได้ง่ายและไม่มีใครบังคับให้มี

## 🧩 6. โครงสร้างข้อมูลของคำอธิบายสูตร

```ts
// src/lib/chang/types.ts
export type FormulaStep = {
  label: string;   // "พื้นที่ห้อง"
  expr: string;    // "A = กว้าง × ยาว"
  subst?: string;  // "A = 4 × 5 = 20 ตร.ม."   ← ต้องเป็นค่าจริงที่ผู้ใช้กรอก
  note?: string;   // "หักช่องเปิดออกก่อนถ้ามี"
};

export type FormulaExplain = {
  summary: string;                  // สูตรหลักบรรทัดเดียว
  steps: FormulaStep[];             // ไล่ทีละขั้น + แทนค่าจริง
  constants?: ConstRef[];           // ดึงจาก constants.ts พร้อมที่มาอัตโนมัติ
  assumptions?: string[];           // สมมติฐานที่สูตรตั้งไว้
  caveats?: string[];               // ข้อจำกัด + คำเตือนชั้น B/C
  refs?: { label: string; url?: string }[];
  risk: "A" | "B" | "C";
  updatedAt: string;                // YYYY-MM-DD ของการทบทวนล่าสุด
};
```

- 🧷 `CalcResult.explain` เป็น **optional** เพื่อให้ 72 เครื่องมือเดิมคอมไพล์ผ่านระหว่างทยอยเติม
- 🧷 สูตรใหม่ใช้ builder `resultX({ title, headline, rows, tip, explain })` ใน `math.ts` · ตัวเดิม `result(headline, rows, tip, title)` ยังอยู่เหมือนเดิมสำหรับสูตรที่ยังไม่เติมคำอธิบาย — ห้ามเพิ่มพารามิเตอร์ตัวที่ 5 ให้ `result()` เพราะถูกเรียกจากทุกไฟล์
- 🧷 `subst` ต้องสร้างจากค่าที่คำนวณจริง ห้าม hardcode ตัวอย่าง ไม่งั้นมันจะโกหกผู้ใช้ทันทีที่เปลี่ยนอินพุต

## 👓 7. หลักการแสดงผล — เข้าใจง่ายแบบเฟรนด์ลี่

### 7.1 บล็อกสูตรแบบหุบ-กาง

- ใช้ `<details>/<summary>` ของ HTML ตรง ๆ ได้คีย์บอร์ดและ screen reader ฟรี ไม่มีปัญหา hydration ตอน SSR และเนื้อหายังอยู่ใน DOM ตอนหุบ (ดีต่อ SEO)
- โปรเจกต์ใช้ Tailwind v4 → ใช้ `group-open:` ได้เลย ไม่ต้องพึ่ง state
- **ค่าตั้งต้นคือหุบ** เพราะคนส่วนใหญ่อยากได้คำตอบก่อน แต่จำสถานะที่ผู้ใช้เลือกไว้ ช่างที่ชอบดูสูตรจะได้ไม่ต้องกดซ้ำทุกหน้า
- ลำดับเนื้อหาในบล็อก: **สูตรหลัก → แทนค่าจริง → ค่าคงที่ที่ใช้ + ที่มา → สมมติฐาน → ข้อควรระวัง → อ้างอิง**
- ตัวเลขใช้ฟอนต์ mono + `tabular-nums` ให้หลักตรงกัน อ่านเทียบง่าย
- หน้า "คิดทั้งงาน" ที่มีหลายผลลัพธ์ ต้องมีปุ่มกาง/หุบทั้งหมด

### 7.3 กราฟประกอบผลลัพธ์ 📊

กราฟมีหน้าที่ **ตอบคำถามที่ตัวเลขเดี่ยวตอบไม่ได้** ไม่ใช่ของประดับ ถ้าดูกราฟแล้วไม่ได้ความรู้เพิ่มจากตาราง ให้ตัดออก

วาดด้วย SVG/CSS ในโปรเจกต์เอง (`src/components/chang/ResultChart.tsx`) **ไม่ใช้ไลบรารีกราฟ** เพราะกราฟที่ต้องใช้เป็นแบบนิ่ง ไม่มี zoom/tooltip ไม่คุ้มกับ JS อีกร้อยกิโลไบต์บนมือถือหน้างานที่เน็ตช้า

| ชนิด | ใช้เมื่อคำถามคือ | ตัวอย่าง |
|---|---|---|
| 🪜 `steps` | "ของที่ขายมีเป็นขั้น ๆ ฉันอยู่ขั้นไหน ห่างขั้นถัดไปแค่ไหน" | ขนาดสายไฟ, ขนาดแอร์ BTU |
| 🚦 `threshold` | "เกินเกณฑ์มาตรฐานหรือยัง เฉียดแค่ไหน" | แรงดันตก 3% / 5% |
| 🧱 `stack` | "ก้อนนี้ประกอบจากอะไร สัดส่วนเท่าไหร่" | ปูน:ทราย:หิน, เนื้ออิฐ:แนวปูน, รองพื้น:ทับหน้า |
| 📦 `packs` | "ซื้อกี่ใบ ใบสุดท้ายใช้จริงเท่าไหร่ เหลือเท่าไหร่" | ถุงปูน, กล่องกระเบื้อง |

**กฎการวาด**

- 🎨 สีมีความหมายเดียวตลอดระบบ — เทาจาง = ยังไม่พอ / ส้ม (forge) = ที่แนะนำ / เขียว = ผ่านเกณฑ์ / เหลือง = เฉียดเกณฑ์ / แดง = เกิน **ห้ามใช้สีเพื่อความสวยล้วน**
- 🔤 มีคำกำกับสีทุกครั้งที่สีเป็นตัวสื่อความหมาย คนตาบอดสีต้องอ่านรู้เรื่องเท่ากัน
- 📏 แกนเริ่มที่ศูนย์เสมอ ห้ามตัดฐานให้ความต่างดูเยอะเกินจริง
- ♿ ทุกกราฟมี `role="img"` + `aria-label` ที่สรุปตัวเลขเป็นคำพูด และตัวเลขทุกตัวในกราฟต้องมีอยู่ในตารางผลลัพธ์ด้วย — **กราฟหายไปแล้วผู้ใช้ต้องยังได้คำตอบครบ**
- 🚫 เลขเดี่ยวที่ไม่มีเกณฑ์ ไม่มีขั้น ไม่มีส่วนประกอบ (เช่น น้ำหนักเหล็ก) **ไม่ต้องมีกราฟ**
- 📐 สเปกกราฟเป็นข้อมูลล้วนใน `CalcResult.chart` แยกจากการวาด เทสจึงตรวจได้ว่าไม่มีค่าเพี้ยน (NaN, ติดลบ, โซนเรียงผิด, ตัวที่เลือกน้อยกว่าที่ต้องการ)

### 7.4 ผลลัพธ์ที่เอาไปใช้ต่อได้

- คัดลอก / แชร์ / บันทึกเป็นรูป ต้องได้ทั้งตัวเลขและหน่วย
- ค่าตั้งต้น **ไม่รวมสูตร** ในข้อความที่ส่งลูกค้า (ลูกค้าไม่ได้อยากอ่าน) แต่มีตัวเลือก "คัดลอกพร้อมสูตร" สำหรับส่งช่างอีกคนหรือแนบใบเสนอราคา

## 🧪 9. การทดสอบ

**สิ่งที่ต้องมี 3 ชั้น**

1. 🎯 **เทสยึดค่า (golden values)** — ตรึงผลลัพธ์ของแต่ละสูตรไว้ ใครขยับค่าคงที่โดยไม่ตั้งใจจะเห็นทันทีว่ากระทบสูตรไหน
2. 🔍 **เทสไล่แคตตาล็อก** — วนทุกเครื่องมือใน catalog แล้วยืนยันว่า *ทุกตัว* มี `explain` และมี `risk` (กันลืมเวลาเพิ่มเครื่องมือใหม่)
3. 📚 **เทสทะเบียนค่าคงที่** — วนทุกรายการใน `constants.ts` แล้วยืนยันว่ามี `source` ไม่ว่าง (กันเลขลอยกลับเข้ามา)

**สถานะปัจจุบัน:** ใช้ Vitest แล้ว — `npm test` (ไฟล์เทส `src/lib/chang/__tests__/calcs.test.ts`)

```bash
npm test         # เทสสูตรทั้งหมด
npm run typecheck
npm run lint
```

เทสที่มีตอนนี้ครอบ 3 ชั้นครบ: ยึดค่าสูตรเรือธง 8 ตัว, ไล่ทุกเครื่องมือในแคตตาล็อกว่ารันด้วยค่าตั้งต้นได้และไม่มี `NaN` หลุดออกหน้าจอ, และไล่ทุกค่าคงที่ว่ามี `source` ไม่ว่าง

ชั้นที่ 4 คือ 📊 **เทสสเปกกราฟ** — ไล่กราฟทุกตัวว่าค่าเป็นตัวเลขจริง โซนเกณฑ์เรียงจากน้อยไปมากและปิดที่ขอบกราฟ กราฟไต่ขั้นมีตัวที่เลือกหนึ่งตัวและตัวที่เลือกต้องไม่น้อยกว่าที่ต้องการ (กันกรณีแนะนำของที่เล็กเกินไปแบบเงียบ ๆ)
